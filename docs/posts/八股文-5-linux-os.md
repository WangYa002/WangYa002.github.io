# Linux 操作系统核心八股

> 操作系统是 C++ 后端面试的"次高频"领域（仅次于 C++ 语言）。本文按"进程线程 → IPC → 调度 → 内存 → 同步"组织，覆盖 90% 高频考点。

---

## 一、进程 vs 线程 vs 协程

### 1.1 三者对比

| 维度 | 进程 | 线程 | 协程 |
| --- | --- | --- | --- |
| 定义 | 资源分配基本单位 | CPU 调度基本单位 | 用户态轻量级线程 |
| 切换者 | 操作系统 | 操作系统 | 用户（库/语言运行时） |
| 切换模式 | 用户态 → 内核态 → 用户态 | 用户态 → 内核态 → 用户态 | 用户态 |
| 调用栈 | 内核栈 | 内核栈 | 用户栈 |
| 拥有资源 | 地址空间、文件句柄、信号量 | PC、寄存器、栈、状态字 | 自己的寄存器上下文和栈 |
| 切换开销 | 大（页表切换、cache 失效） | 小（保存少量寄存器） | 极小（栈拷贝） |
| 通信方式 | IPC（管道、共享内存、信号量） | 直接读写共享变量 | 共享内存/消息队列 |

### 1.2 为什么要有线程

1. **进程切换开销大**：保存/恢复虚拟地址空间、页表、cache
2. **进程间通信复杂**：必须通过内核
3. **进程崩溃影响其他进程**：隔离性强但通信成本高

线程引入：
- 共享地址空间 → 直接读全局变量
- 切换只保存少量寄存器 → 开销小
- 创建/销毁比进程快 10-100 倍

### 1.3 协程的本质

```cpp
// C++20 协程
Task<int> compute() {
    int x = co_await fetch_async();
    int y = co_await compute_async(x);
    co_return x + y;
}
```

**协程 vs 线程**：
- 协程在**用户态切换**，无需内核介入
- 协程**非抢占式**：由程序员控制何时让出（`co_await`）
- 单线程内可有上百万协程，但线程一般几百到几千

**有栈协程 vs 无栈协程**：

| 类型 | 栈空间 | 挂起/恢复 | 代表 |
| --- | --- | --- | --- |
| 有栈（stackful） | 每个协程独立栈（固定大小） | 任意函数深度 | goroutine、Boost.Coroutine |
| 无栈（stackless） | 共享线程栈 | 只能在协程函数内 | C++20 coroutine、Python async |

### 1.4 多进程 vs 多线程选择

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 频繁创建销毁 | 多线程 | 线程开销小 |
| 大量 CPU 计算 | 多线程 | 多核利用 |
| 任务强相关、共享数据多 | 多线程 | 通信简单 |
| 任务弱相关、稳定性要求高 | 多进程 | 进程崩溃不影响其他 |
| 需要多机扩展 | 多进程 | 进程可独立部署 |

**典型应用**：
- Nginx：多进程（master + workers），稳定+并发
- Chrome：多进程，每个 tab 一个进程，隔离
- Redis：单进程单线程，避免锁

## 二、进程间通信（IPC）

### 2.1 七种 IPC 对比

| 方式 | 速度 | 范围 | 特点 |
| --- | --- | --- | --- |
| **管道（pipe）** | 中 | 父子进程 | 半双工，字节流 |
| **命名管道（FIFO）** | 中 | 同主机 | 半双工，任意进程 |
| **消息队列** | 中 | 同主机 | 消息为单位，支持优先级 |
| **共享内存** | **最快** | 同主机 | 零拷贝，需同步机制 |
| **信号量** | 慢 | 同主机 | 计数器，用于同步 |
| **信号** | 极快 | 同主机 | 异步通知，信息量小 |
| **Socket** | 慢 | 跨主机 | 通用，TCP/UDP |

### 2.2 共享内存为什么最快

```text
普通 IPC（消息队列）：
进程 A → 内核（拷贝1） → 内核（拷贝2） → 进程 B

共享内存：
进程 A → 共享内存段 ← 进程 B   （直接读写，无需拷贝）
```

**关键**：共享内存通过 `mmap` 把同一块物理内存映射到不同进程的虚拟地址空间，访问时**无需进入内核态**。

但需要配合**信号量或互斥锁**保证同步：

```cpp
// 进程 A
sem_wait(&sem);
shared_data->count++;
sem_post(&sem);

// 进程 B 同上
```

### 2.3 管道 vs 命名管道

```cpp
// 匿名管道：只能父子进程
int fd[2];
pipe(fd);
if (fork() == 0) {
    close(fd[0]);
    write(fd[1], "hello", 5);
} else {
    close(fd[1]);
    char buf[10];
    read(fd[0], buf, 5);
}

// 命名管道：任意进程
mkfifo("/tmp/myfifo", 0666);
int fd = open("/tmp/myfifo", O_WRONLY);
write(fd, "hello", 5);
```

### 2.4 TCP 粘包/拆包

TCP 是**字节流协议**，没有消息边界。常见解法：

```cpp
// 方案 1：固定长度（效率低）
char buf[1024];
read(fd, buf, 1024);

// 方案 2：分隔符（如 HTTP 的 \r\n）
std::string line;
std::getline(stream, line);

// 方案 3：长度前缀（最常用）
struct Header {
    int32_t magic;     // 魔数，校验
    int32_t length;    // 包体长度
};
read(fd, &header, sizeof(header));
std::vector<char> body(header.length);
read(fd, body.data(), header.length);
```

**为什么 HTTP/1.1 解决了粘包**：

- HTTP/1.0 短连接：读完响应直接关闭，下个响应必然在新连接
- HTTP/1.1 长连接：用 `Content-Length` 或 `Transfer-Encoding: chunked` 明确边界

## 三、调度算法

### 3.1 5 大调度算法

| 算法 | 抢占 | 特点 | 缺点 |
| --- | --- | --- | --- |
| **FCFS** 先来先服务 | ❌ | 简单公平 | 短任务饿死 |
| **SJF** 短作业优先 | ❌ | 平均等待最短 | 长任务饿死 |
| **SRTN** 最短剩余时间优先 | ✅ | SJF 抢占版 | 切换开销大 |
| **优先级调度** | ✅/❌ | 灵活 | 低优先级饿死 |
| **时间片轮转** | ✅ | 公平，响应快 | 时间片太小，切换开销大 |

**Linux 调度器演进**：
- O(1) 调度器（2.6 开始）：每 CPU 维护优先级队列
- CFS（完全公平调度，2.6.23）：基于红黑树，按虚拟运行时间排序

### 3.2 CFS 原理

```text
所有可运行进程按 vruntime 排在红黑树
vruntime 越小 = "亏欠" CPU 时间越多 = 优先调度

每次时钟中断：
  current->vruntime += 实际运行时间 * 优先级权重

调度时机：
  挑红黑树最左节点（vruntime 最小）
```

**优势**：
- 真正的"公平"
- O(log n) 调度复杂度
- 优先级通过权重体现，nice 值越低权重越高

### 3.3 进程/线程的状态

```text
       创建
        │
        ↓
     ┌──────┐
     │ 新建 │
     └──┬───┘
        ↓
     ┌──────┐  时间片到/被抢占  ┌──────┐
     │ 就绪 │ ←─────────────── │ 运行 │
     └──┬───┘                   └──┬───┘
        │                          │
        │     调度器选中            │
        └──────────────→           │
                                   │ I/O 等待/wait
                                   ↓
                                ┌──────┐
                                │ 阻塞 │
                                └──┬───┘
                                   │ 资源就绪
                                   ↓
                                ┌──────┐
                                │ 就绪 │
                                └──────┘
```

### 3.4 僵尸进程与孤儿进程

| 概念 | 定义 | 危害 | 解决 |
| --- | --- | --- | --- |
| **孤儿进程** | 父进程已退出，子进程还在运行 | 无害（init 收养） | 无需处理 |
| **僵尸进程** | 子进程已退出，父进程未 `wait` | 占用 PID，过多导致无法 fork | 杀死父进程或注册 SIGCHLD |

**僵尸进程处理**：

```cpp
// 方案 1：父进程注册 SIGCHLD 处理函数
signal(SIGCHLD, [](int) {
    while (waitpid(-1, nullptr, WNOHANG) > 0);
});

// 方案 2：fork 两次（让子进程变孤儿）
if (fork() == 0) {
    if (fork() == 0) {
        // 孙子进程干活，父进程（儿子）立即退出
        // 孙子被 init 收养，不会变僵尸
        do_work();
        exit(0);
    }
    exit(0);
}
wait(nullptr);  // 回收儿子
```

## 四、虚拟内存

### 4.1 为什么需要虚拟内存

```text
没有虚拟内存：
进程 A 直接访问物理内存 0x1000
进程 B 也要访问 0x1000  → 冲突！

有虚拟内存：
进程 A 的 0x1000 → 页表 → 物理内存 0x5000
进程 B 的 0x1000 → 页表 → 物理内存 0x9000
各自独立，互不干扰
```

**核心收益**：
1. 进程隔离（安全性）
2. 内存"放大"：用磁盘做交换区，可运行大于物理内存的程序
3. 共享内存：多个虚拟页映射到同一物理页（如共享库）

### 4.2 分页机制

```text
虚拟地址（64 位下通常用 48 位）：
┌────────────────┬──────────┐
│   页号 (VPN)    │ 页内偏移 │
│   36 位         │ 12 位    │
└────────────────┴──────────┘

页表：VPN → PFN（物理页帧号）
物理地址 = PFN * 页大小 + 偏移
```

**页大小**：x86-64 默认 4KB，huge page 可设 2MB 或 1GB。

### 4.3 多级页表

为什么不直接用一级页表？

```text
48 位虚拟地址 + 4KB 页：
- 1 级页表项数 = 2^36 = 64 G 项
- 每项 8 字节 = 512 GB / 进程

显然不行！
```

**4 级页表**（x86-64 Linux）：

```text
48 位虚拟地址：
┌──────┬──────┬──────┬──────┬──────────┐
│ PGD  │ PUD  │ PMD  │ PTE  │  Offset  │
│ 9位  │ 9位  │ 9位  │ 9位  │  12 位   │
└──────┴──────┴──────┴──────┴──────────┘

PGD → PUD → PMD → PTE → 物理页
每级 9 位 = 512 项（一个页）
```

**优势**：
- 大部分进程不会用满 48 位地址空间
- 未使用的中间页表项可以不分配，省内存
- 经典的"时间换空间"

### 4.4 TLB（快表）

TLB（Translation Lookaside Buffer）是 CPU 内部的**页表项缓存**：

```text
虚拟地址 → 查 TLB
            ↓
        命中？─── 是 → 直接拿物理地址
            │
            否
            ↓
        查页表（多次内存访问，慢）
            ↓
        更新 TLB
```

**关键**：
- TLB 容量小（通常 64-1024 项）
- 进程切换时 TLB 全部失效（不同进程页表不同）
- 这就是**线程切换比进程快**的核心原因！

### 4.5 缺页中断

```text
1. CPU 访问虚拟地址
2. 查 TLB 未命中
3. 查页表发现"present"位为 0
4. 触发缺页中断（page fault）
5. 内核检查该地址是否合法：
   - 非法 → SIGSEGV（段错误）
   - 合法但页不在内存：
     a. 从磁盘换入（swap）
     b. 或首次访问，分配新页
6. 更新页表，恢复执行
```

**写时复制（Copy-on-Write）**：

```cpp
pid_t pid = fork();
// fork 时父子进程共享同一物理页，标记为只读
// 任一方写入 → 触发缺页中断 → 内核分配新页
```

### 4.6 页面置换算法

当物理内存不足，需要换出某页。常见算法：

| 算法 | 描述 | 实际应用 |
| --- | --- | --- |
| **OPT** 最佳置换 | 淘汰以后最长时间不用的页 | 理论，不可实现 |
| **FIFO** 先进先出 | 淘汰最早进入的页 | 简单，但可能淘汰热页 |
| **LRU** 最近最久未使用 | 淘汰最久没访问的 | 接近 OPT，但实现开销大 |
| **Clock** 时钟算法 | LRU 的近似，环形扫描 | Linux 实际使用 |
| **LFU** 最少使用频率 | 淘汰访问次数最少的 | 容易受历史数据影响 |

**LRU 真实实现挑战**：
- 每次访问都要更新链表 → 太贵
- Linux 用 Clock（第二次机会）算法近似 LRU

## 五、上下文切换

### 5.1 三种上下文切换

| 类型 | 触发 | 切换内容 | 开销 |
| --- | --- | --- | --- |
| **进程切换** | 时间片到、阻塞、调度 | 全套寄存器 + 页表 + 内存管理单元状态 | 大（~几 μs） |
| **线程切换** | 同上 | 寄存器 + 栈指针 | 中 |
| **中断切换** | 硬中断 | 寄存器 + 内核栈 | 小 |

### 5.2 进程切换为什么慢

```text
进程切换流程：
1. 保存当前进程上下文（寄存器、PC、SP）
2. 切换页表（写 CR3 寄存器）
3. ★ TLB 全部失效（不同进程页表不同）
4. ★ cache 大量失效
5. 加载新进程上下文
6. 跳转到新进程的 PC
```

**TLB 失效是性能杀手**：之后每次内存访问都要查多级页表（4 次内存访问）。

**优化**：
- PCID（Process Context Identifier）：给页表加 ID，TLB 不全部失效
- 透明大页：减少页表项数量

### 5.3 系统调用 vs 普通函数调用

| 维度 | 系统调用 | 普通函数 |
| --- | --- | --- |
| 进入方式 | 软中断（int 0x80）或 syscall 指令 | call 指令 |
| 切换 | 用户态 → 内核态 → 用户态 | 同一特权级 |
| 开销 | ~100-200 ns（两次上下文切换） | ~1 ns |
| 栈 | 切到内核栈 | 同一栈 |

**优化**：
- vDSO：常见系统调用（如 `gettimeofday`）映射到用户态，无需切换
- io_uring：批量提交 I/O 请求，减少 syscall 次数

## 六、线程同步

### 6.1 死锁的 4 个必要条件

```text
1. 互斥：资源同一时刻只能被一个进程使用
2. 占有并等待：持有资源的同时等待其他资源
3. 不可剥夺：资源只能自愿释放
4. 循环等待：A 等 B，B 等 C，C 等 A
```

**破除任一条件即可避免死锁**：

| 条件 | 破除方法 |
| --- | --- |
| 互斥 | 通常无法破除（资源特性） |
| 占有并等待 | 一次性申请所有资源 |
| 不可剥夺 | 申请不到就释放已有资源（`try_lock`） |
| 循环等待 | 统一加锁顺序（按地址/ID） |

### 6.2 经典死锁场景

```cpp
// 死锁：交叉锁
std::mutex m1, m2;

void thread_a() {
    std::lock_guard<std::mutex> l1(m1);
    // ... 此处被切走
    std::lock_guard<std::mutex> l2(m2);   // 等 m2
}

void thread_b() {
    std::lock_guard<std::mutex> l2(m2);
    std::lock_guard<std::mutex> l1(m1);   // 等 m1 → 死锁
}

// 修复 1：统一顺序
void thread_b() {
    std::lock_guard<std::mutex> l1(m1);   // 先 m1 再 m2
    std::lock_guard<std::mutex> l2(m2);
}

// 修复 2：std::lock（C++11，原子地获取多个锁）
std::lock(m1, m2);
std::lock_guard<std::mutex> l1(m1, std::adopt_lock);
std::lock_guard<std::mutex> l2(m2, std::adopt_lock);
```

### 6.3 互斥锁的底层实现

```cpp
// futex（Fast Userspace Mutex）原理
void lock() {
    while (true) {
        // 快路径：用户态 CAS，期望 0 → 1
        if (cas(locked_, 0, 1) == 0) return;
        
        // 慢路径：调用 futex 系统调用，挂起当前线程
        futex_wait(&locked_, 1);
    }
}

void unlock() {
    locked_ = 0;
    futex_wake(&locked_, 1);   // 唤醒一个等待者
}
```

**优势**：
- 无竞争时纯用户态，极快
- 有竞争时才陷入内核
- 适合"竞争不激烈"的场景

### 6.4 自旋锁 vs 互斥锁

| 类型 | 实现 | 适用场景 |
| --- | --- | --- |
| **自旋锁** | 死循环 CAS | 临界区极短（< 10 ns） |
| **互斥锁** | 自旋几次后挂起 | 临界区较长 |
| **混合锁** | 自旋 + 挂起 | Linux pthread_mutex 默认 |

```cpp
// 自旋锁实现
class SpinLock {
    std::atomic<bool> locked_{false};
public:
    void lock() {
        while (locked_.exchange(true, std::memory_order_acquire)) {
            // 持续 spin，但加 pause 指令降低功耗
            __builtin_ia32_pause();
        }
    }
    void unlock() {
        locked_.store(false, std::memory_order_release);
    }
};
```

### 6.5 条件变量虚假唤醒

```cpp
std::mutex mtx;
std::condition_variable cv;
bool ready = false;

// ❌ 错误：可能虚假唤醒
{
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock);                  // 可能虚假唤醒后继续执行
    // do work
}

// ✅ 正确：用谓词或循环
{
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, [&] { return ready; });   // 内部循环检查
    // do work
}

// 等价于
{
    std::unique_lock<std::mutex> lock(mtx);
    while (!ready) cv.wait(lock);
    // do work
}
```

**为什么有虚假唤醒**：
- POSIX 标准允许，实现上更简单（中断可打断 wait）
- 防止某些边界场景的死锁

### 6.6 原子操作 6 种内存序

| 内存序 | 含义 |
| --- | --- |
| `memory_order_relaxed` | 无同步，仅保证原子 |
| `memory_order_consume` | 类似 acquire，但只对依赖操作（很少用） |
| `memory_order_acquire` | 后续读写不能重排到本操作之前 |
| `memory_order_release` | 前序读写不能重排到本操作之后 |
| `memory_order_acq_rel` | 同时 acquire + release（read-modify-write） |
| `memory_order_seq_cst` | 全局顺序一致（最强，默认） |

```cpp
// 单生产者单消费者，发布/订阅模式
std::atomic<int> data{0};
std::atomic<bool> ready{false};

// 生产者
data.store(42, std::memory_order_relaxed);
ready.store(true, std::memory_order_release);

// 消费者
while (!ready.load(std::memory_order_acquire));
assert(data.load(std::memory_order_relaxed) == 42);   // 一定成立
```

## 七、面试高频追问链

### Q1：为什么共享内存是最快的 IPC？

> 共享内存通过 `mmap` 把同一块物理内存映射到多个进程的虚拟地址空间。读写时直接访问内存，**无需内核参与、无需拷贝**。但需要配合信号量/互斥锁保证同步。

### Q2：僵尸进程的危害？

> 子进程退出后，内核保留其退出状态（PID、退出码、运行时间），等待父进程 `wait`。如果父进程不 `wait`，这些信息会一直占用 PID 资源。系统 PID 数量有限（默认 32768），僵尸进程过多会导致无法 `fork`。

### Q3：进程切换为什么比线程切换慢？

> 进程切换需要切换**页表**，导致 **TLB 全部失效**。TLB 失效后每次内存访问都要查多级页表（4 次内存访问），性能急剧下降。线程共享页表，切换时 TLB 不失效。

### Q4：协程为什么不能利用多核？

> 协程本质是单线程内的"用户态线程"，由用户调度。一个线程同一时刻只能跑一个协程。要多核并行，需要开多线程，每个线程内跑多个协程。Go 的 goroutine 是 M:N 模型，多个 goroutine 在多个内核线程上调度。

### Q5：缺页中断一定会触发磁盘 I/O 吗？

> 不一定。
> - 首次访问：分配新页，从 0 填充（不读磁盘）
> - 写时复制：分配新页，从源页拷贝
> - swap 换入：从磁盘读取
> - 文件 mmap：从文件读取

### Q6：自旋锁一定比互斥锁快吗？

> 不是。自旋锁适合**临界区极短**（< 10 ns）且**CPU 资源充足**的场景。临界区长或单核机器上，自旋会浪费 CPU 时间。Linux 内核的 spinlock 适合中断上下文（不能睡眠），用户态一般用 mutex。

### Q7：条件变量为什么要配合 mutex？

> 1. 防止**信号丢失**：先 lock 再 wait，避免在 check 和 wait 之间被信号通知
> 2. wait 内部会**释放 mutex**，让其他线程能修改共享状态；被唤醒时**重新获取 mutex**
> 3. 共享状态（如 `ready` 标志）本身需要锁保护

### Q8：什么是 false sharing？

> 多核 CPU 中，每个核有自己的 L1/L2 cache，以**缓存行（64 字节）**为单位同步。两个变量在同一缓存行，一个核修改变量 A，会导致另一个核的整个缓存行失效，影响变量 B 的读取。

```cpp
// ❌ false sharing
struct Counters {
    int a = 0;     // 线程 1 写
    int b = 0;     // 线程 2 写
};                  // a 和 b 可能在同一缓存行

// ✅ 缓存行对齐
struct alignas(64) Counters {
    int a = 0;
    int b = 0;
};
```
